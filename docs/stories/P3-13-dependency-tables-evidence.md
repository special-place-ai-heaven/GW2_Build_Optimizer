# Story 3.13: Factorized Dependency Tables and Evidence Classification

Status: ready-for-dev

## Story

As a GW2 player,
I want every numeric rule in the optimizer to be classified by evidence level and every data table to be cross-validated against the others,
so that I can trust that the optimizer knows the difference between verified facts, derived computations, and heuristic guesses — and that no data file references an entity that doesn't exist.

## Non-Goals

- **No new data tables** -- rotation profiles, objective profiles, scoring rules are Phase C.
- **No numeric value changes** -- only classifies, validates, and flags.
- **No UI changes** -- reports and tests only.
- **No Phase C table classification** -- documents them as deferred.

## Dependencies

- **All Phase A (P3-01 through P3-06)** (done) -- data tables to classify.
- **P3-07 (done)** -- typed loaders.
- **P3-08 (done)** -- patch manifest/ledger.
- **P3-09 (done)** -- balance overrides, FactualValue, DataQuality.
- **P3-10a (done)** -- NormalizedEffect type system.
- **P3-10b (done)** -- populated effect data.
- **P3-12 (done)** -- WvW audit artifact.
- **Downstream**: P3-15 (scorer isolation consumes evidence classification).

## Acceptance Criteria

1. Every numeric rule across all data tables has an `evidence_level` classified as Factual, Derived, Heuristic, or Unknown.
2. Summary report committed at `docs/reports/p3-13-evidence-classification.md` listing: table name, total entries, count per evidence level, unclassified/inconsistent entries.
3. Every Heuristic entry is named, documented (states the assumption), and replaceable.
4. Every Unknown entry documents why it is unknown and what would resolve it.
5. No entry has a missing or empty evidence level — classification is exhaustive.
6. Cross-file consistency tests (as `cargo test`):
   a. Every profession referenced in any data file exists in profession_profiles.json.
   b. Every patch override file references a valid patch manifest.
   c. Every normalized effect file references a valid patch and mode.
   d. Every normalized effect entry's category is a valid EffectCategory variant.
   e. Balance override entity source_type/source_id resolves (where applicable).
7. Blocking failures fail tests: missing manifest ref, invalid patch_id/mode, nonexistent source entity, source type mismatch, Factual without source citation, schema structural mismatch.
8. Non-blocking findings documented in report: evidence-quality upgrade opportunities, deferred Phase C tables, P3-12 audit gaps, P3-10b coverage gaps.
9. P3-12 WvW audit integration: coefficients flagged as "uncertain split status" classified with appropriate evidence levels. Unresolvable → Unknown (not Heuristic).
10. Table coverage verified: profession_profiles, slot_budgets, universal formulas, condition/boon formulas, balance_overrides, normalized_effects all exist and load. Rotation_profiles, objective_profiles, scoring_rules noted as deferred to Phase C.
11. Every Factual entry has at least one source citation. Every Derived entry documents derivation method. Factual without source → downgraded (blocking failure).
12. Report generated by deterministic command (cargo test output or committed script), includes per-table breakdown and cross-table summary.

### Evidence Level Definitions (from data/mod.rs)

- **Factual**: Verified from official source (wiki, API, patch notes). Must have source citation.
- **Derived**: Computed from factual data using documented method.
- **Heuristic**: Estimated/assumed value. Must be documented and replaceable.
- **Unknown**: Value not yet determined. Must document what would resolve it.

### P3-12 Audit Integration

The WvW audit at `docs/reports/p3-12-wvw-non-fallback-audit.md` classifies paths as:
- (a) uses WvW data — already classified
- (b) mode-invariant base — safe, Factual/Derived
- (c) known split but WvW unresolved — classify as Unknown
- (d) uncertain split status — classify appropriately per evidence rules

## Dev Notes

- This story is primarily AUDIT AND VALIDATION, not new feature implementation.
- The report is the primary deliverable alongside the tests.
- Boon/condition formulas are inline in Rust code, not JSON files. Their evidence classification is documented in the report but may not have a `evidence_level` field per entry — classify by code review.
- For baseline data files (balance_overrides are empty, normalized_effects have representative entries), the classification reflects what's actually there, not aspirational coverage.
- Cross-file consistency tests should use the existing loaders to load data, then validate references.
- Don't over-engineer: tests load data, check references, assert consistency. Report is markdown generated from test output or a dedicated test that writes markdown.
