# Story 3.12: WvW Non-Fallback Behavior

Status: ready-for-dev

## Story

As a GW2 WvW player,
I want the optimizer to use WvW-specific balance data when it exists and explicitly degrade when it doesn't,
so that I never receive PvE-tuned results silently presented as WvW recommendations.

## Non-Goals

- **No new WvW balance data files** -- data authoring is separate from this story.
- **No WvW rotation profiles** -- that is P3-14.
- **No WvW objective profiles** -- that is P3-15.
- **No UI changes** -- DataQuality surfaces through existing output types.
- **No re-implementation of lookup semantics** -- P3-09 already enforces None-not-PvE for missing overrides.

## Dependencies

- **P3-02 (done)** -- BalanceContext for mode dispatch.
- **P3-09 (done)** -- Balance override infrastructure with None-vs-Unknown semantics.
- **Downstream**: P3-13 (evidence classification consumes audit findings).

## Acceptance Criteria

1. WvW optimization uses WvW-specific balance data when available.
2. When no WvW override exists AND no known mode split exists, base Phase A value is used (safe, may remain Verified).
3. When a known mode split exists but WvW value is missing/unresolved, computation degrades to Provisional or Blocked with a DataQualityReason citing the unresolved split.
4. No code path silently substitutes PvE override values for missing WvW overrides.
5. Audit artifact committed at `docs/reports/p3-12-wvw-non-fallback-audit.md` listing every mode-sensitive computation path reachable during WvW optimization, classified as: (a) uses WvW data, (b) mode-invariant base (safe), (c) known split but WvW unresolved, (d) uncertain split status.
6. The audit is reproducible (generated by a test or deterministic analysis, not hand-authored).
7. Integration tests: WvW-resolved lookup, known-split-missing degrades quality, no-known-split uses base value.
8. All WvW computation paths go through BalanceContext-parameterized functions.

## Technical Context

### P3-09 Infrastructure Review

The `BalanceOverrides` system from P3-09 already enforces:
- Lookup keyed by `(patch_id, mode)` -- no cross-mode fallback
- `None` return = no override exists (use base value, no quality impact)
- `Some(Unknown)` return = explicitly unresolved (degrades quality)

This story validates that this infrastructure produces correct WvW behavior end-to-end and adds enforcement for "known mode splits."

### Known Mode Splits

In GW2, some coefficients differ between PvE and competitive modes (PvP/WvW). Examples:
- Fury crit bonus: 25% PvE, 20% PvP/WvW (already handled by P3-04 `fury_crit_bonus()`)
- Protection damage reduction: 33% PvE, 33% PvP/WvW (same in both, but could diverge)
- Various skill/trait coefficients split by ArenaNet in balance patches

The known-split enforcement means: if a coefficient is KNOWN to have been split between modes (documented in patch ledger or balance overrides), and the WvW value is missing, the system must not silently use PvE data. Instead, it returns Unknown and degrades DataQuality.

### Implementation Approach

1. **Audit**: Trace every mode-sensitive computation path in the optimizer that WvW can reach. These include:
   - `combat.rs` functions that accept `BalanceContext` (fury, protection, resolution, might, etc.)
   - `boon_condition_formulas.rs` mode-dependent lookups
   - `universal_formulas.rs` mode-dependent values (if any)
   - Balance override lookups in scoring/stat calculation

2. **Known-split registry**: Create a small data structure (could be a test-only constant or a data file) that lists coefficients known to differ between modes. For now, this can be inline in the audit test.

3. **Integration tests**: Use P3-09's BalanceOverrides with test fixtures that include WvW-specific entries, then verify correct behavior.

4. **DataQuality enforcement**: When a known-split coefficient has no WvW override, the optimizer should produce `DataQuality::Provisional` with an appropriate `DataQualityReason`.

### Where Code Lives

- Primary: `crates/optimizer/src/` -- integration tests and any enforcement code
- Audit: `docs/reports/p3-12-wvw-non-fallback-audit.md` -- generated report
- Tests: in the optimizer test module or a dedicated test file

## Dev Notes

- This story is primarily about VALIDATION and AUDIT, not new feature implementation. P3-09 already built the infrastructure.
- The audit is the primary deliverable. It should list every path and classify it.
- For the baseline (2026-01-13), there are no known mode splits in the balance_overrides data (all empty). The integration tests should use synthetic fixture data.
- The "known-split registry" could be:
  (a) A data file `data/known_mode_splits.json` listing coefficients known to differ
  (b) Inline constants in the enforcement module
  (c) Entries in the balance_overrides files with `evidence_level: Unknown`
  Option (c) is cleanest -- a known split with unknown WvW value IS an Unknown override entry.
- BalanceContext already parameterizes fury, protection, resolution etc. by mode. These are implemented in P3-04's boon formulas. Verify they use WvW-specific values (which are same as PvP competitive values in GW2).
- Don't over-engineer: the audit can be a markdown file generated by examining the code, not a complex runtime system.
